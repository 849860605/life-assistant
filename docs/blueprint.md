## 1. 定位与原则

聊天能力拼不过豆包、元宝这些通用 App，这个助手的价值放在三件事上：

| 能力 | 说明 |
|---|---|
| **长期记住你** | 体能、忌口、预算习惯、家人情况、常住地。记忆可查看、可修改、可删除 |
| **主动找你** | 爬山前一天山顶有雷暴就提醒改期；训练日提醒你，错过了自动顺延；每周日推送训练复盘 |
| **帮你办事** | 写进日程、记账、生成行程和训练计划；以后叫跑腿、准备外卖订单。付款始终由你自己完成 |

### 设计原则

1. **接口按产品设计，实现按自用来做。** 以后改代价大的地方现在就做对，其余先用最简单的实现。
2. **沿数据关联扩展。** 下一个技能要和已有技能共享数据（行程生成日程，旅行花费进入记账），不按功能清单铺开。
3. **敏感操作必须确认。** 下单、预订、发消息之前，Graph 中断并展示预览，用户确认后才执行。
4. **做不了的先预留。** 平台没开放的能力，只定义接口和配置位，等开放后作为新实现接入，上层代码不改。
5. **不碰微信和支付类 App。** GUI Agent 的白名单里永久排除它们，不自动付款。

## 3. 技能地图

每个技能是一个独立模块，包含一张子图、一组工具和自己的表，通过 `LifeSkill` 接口注册到平台。

| 技能 | 阶段 | 现在能做 | 预留 |
|---|---|---|---|
| **出游** | S0 | 行程规划、天气、地图路线、爬山时间反推与风险评估、行程版本化；酒店用高德搜索位置和评分，再跳转平台查价 | 酒店多平台比价和降价提醒（需要酒店平台数据源） |
| **日程提醒** | S0 | 对话里增改日程；行程和训练计划自动生成日程；ICS 订阅链接让系统日历同步（链接带个人令牌）。日程存储和提醒调度属于平台核心，这个技能只是对话入口 | CalDAV 双向同步 |
| **内容总结** | S1 | 小红书、点评的分享链接或截图，总结成攻略要点，存入知识库，规划出游时检索 | 官方内容接口（目前未开放） |
| **外卖探店** | ⏸ 延后 | 启动后：按记忆推荐吃什么（减脂期按热量和蛋白质筛选），生成跳转链接；GUI Agent 操作美团 App，停在付款页 | 美团外卖官方下单能力；小程序跳转与联盟分佣 |
| **跑腿** | ⏸ 延后 | 启动后：美团跑腿 Skill，帮取送、帮忙、帮买，下单前预览确认 | 无 |
| **健身运动** | S1 | 生成训练计划、对话记录训练、按完成情况自动调整、训练提醒、周复盘；爬山和跑步计入训练量，更新体能画像，反过来影响爬山难度推荐。详见第 13 节 | Apple 健康、Health Connect、手表数据接入 |
| **记账** | S1 | 旅行账单与 AA；日常消费记录；小票拍照识别；外卖、跑腿订单自动记账（随外卖启动） | 账单文件导入（微信、支付宝导出） |

## 4. 执行层分级

同一件事可能有几种做法。执行路由按顺序选第一个可用的方式，失败了自动降级到下一级。

| 级别 | 方式 | 说明 |
|---|---|---|
| ① | 官方接口 / Skill | 高德 MCP、天气 API，以后加上美团跑腿 Skill。最稳定，也最合规 |
| ② | 半自动 | AI 做决定，生成跳转链接或搜索词，用户点一下自己完成。零风险，任何阶段都能用 |
| ③ | GUI Agent | 安卓闲置手机，Qwen-VL 看屏幕、ADB 点击。只操作白名单 App，遇到支付页强制停下并推送确认。仅限自用 |
| 🔲 | 预留位 | 美团外卖官方能力、微信小程序跳转与联盟分佣、端侧 GUI（产品阶段在用户自己的手机上执行）。平台开放后插入 ① 或 ② 的位置 |

| 动作 | 当前执行顺序 | 预留的插入位置 |
|---|---|---|
| 点外卖 | ⏸ 延后；启动后为 ② 半自动跳转 → ③ GUI Agent | 美团外卖官方能力放在最前；产品阶段 ② 改为跳转小程序 |
| 帮买 / 帮送 | ⏸ 延后；启动后为 ① 美团跑腿 Skill | 无 |
| 订酒店 | ② 高德搜索酒店，跳转平台查价预订 | 酒店平台接口（多平台比价） |
| 看小红书 / 点评 | ② 分享链接或截图总结（S1）；③ GUI Agent 搜索随设备执行延后 | 官方内容接口（目前未开放） |
| 写日程 | ① 本地日程 + ICS 订阅 | CalDAV 同步 |

执行顺序由配置决定，预留实现以后直接加在列表前面：

```yaml
life:
  executors:
    hotel:      [semi-auto-link]                 # 以后插入 ctrip / fliggy
    content:    [share-parse]                    # 设备执行启动后追加 gui-agent
    food-order: []                               # 延后；启动时为 [semi-auto-link, gui-agent]，以后插入 meituan-food-official
    errand:     []                               # 延后；启动时为 [meituan-paotui-skill]
```

## 6. 技术选型

### 6.1 版本策略

- 开工时一次性锁定所有依赖版本，记录在根 `pom.xml` 和本节，之后升级单独评估。
- 选**发布满两周以上的最新稳定版**，不用里程碑版、快照版。
- 以 **Spring AI Alibaba 当前稳定版**为基准：它要求哪个 Spring Boot 和 Spring AI 版本，就用哪个，其余依赖跟着它走。版本由官方 BOM（`spring-ai-alibaba-bom`）统一管理。
- JDK 用 21（LTS）。如果当时的 Spring AI Alibaba 已经正式支持 JDK 25（LTS），可以直接用 25。
- Spring AI Alibaba 迭代快，Graph、MCP 的 API 在版本之间有变化，写代码时对照锁定版本的官方示例。

**已锁定的版本（2026-10-27，S0 骨架）：**

| 依赖 | 版本 | 说明 |
|---|---|---|
| Spring AI Alibaba | 1.1.2.4-security-fix | 1.1.2.x 是最新稳定线；2.0.0 目前还是里程碑版，不用 |
| Spring AI | 1.1.2 | 和 Spring AI Alibaba 1.1.2.x 对齐 |
| Spring Boot | 3.5.16 | Spring AI Alibaba 1.1.2.x 要求 Boot 3.5 |
| Sa-Token | 1.46.0 | |
| MyBatis-Plus | 3.5.17 | 3.5.18 发布不满两周，暂不用 |
| ShedLock | 6.10.0 | 7.x 面向 Spring 7 |
| SpringDoc | 2.8.17 | 2.x 对应 Boot 3 |
| PostgreSQL | 17（pgvector/pgvector:pg17 镜像） | |
| Redis | 7.4 | |
| JDK | 编译目标 21 | 本机用 JDK 21 或更高版本都可以 |

### 6.2 后端

| 类别 | 选型 | 理由 | 以后 / 备选 |
|---|---|---|---|
| 语言与构建 | Java 21、Maven 多模块 | 和 Spring AI Alibaba 生态一致；多模块便于技能插拔 | 无 |
| 应用框架 | Spring Boot（版本跟随 Spring AI Alibaba） | 无 | 无 |
| Web | Spring MVC；Controller 返回 `Flux<ServerSentEvent>` 实现流式输出 | 能用 Sa-Token 的标准 starter；比 WebFlux 简单 | 无 |
| AI 框架 | Spring AI Alibaba：DashScope starter、Graph（编排、中断、断点）、MCP Client | 见 6.9 决策记录 | 无 |
| 鉴权 | Sa-Token + Redis（不透明 Token） | 多端登录、踢下线、封禁开箱即用 | 对外开放时加认证中心 + Spring Security 资源服务器 |
| ORM | MyBatis-Plus；`jsonb` 字段用自定义 TypeHandler | SQL 可控，复杂查询和 JSON 字段方便 | Spring Data JPA |
| 数据库迁移 | Flyway，每个模块自带迁移目录 | 换环境、给别人部署时自动建表 | 无 |
| 外部接口调用 | Spring `RestClient` + Resilience4j（重试、熔断、限速） | 天气、地图等外部接口有配额和波动 | 无 |
| 定时任务 | `@Scheduled` + ShedLock（JDBC 锁，存 PostgreSQL） | 不用额外部署服务；多实例时防止重复执行 | 任务多了再上 XXL-Job |
| 接口限流 | Redis 计数 | 自用阶段只记录，S2 起生效 | Bucket4j |
| 敏感字段加密 | 应用层 AES-GCM，密钥来自环境变量 | 密钥不进数据库，数据库泄露也读不出明文 | 云 KMS |
| 接口文档 | SpringDoc OpenAPI | 开放 API 时直接可用 | 无 |
| 配置与密钥 | Spring Profiles + `.env`（不提交到仓库） | 无 | Nacos 配置中心 |

### 6.3 AI 与模型

**模型不绑定厂商。** `ChatModelRegistry` 按 `life.llm.providers` 给每个提供方建一个客户端：`dashscope` 走百炼原生接口，`openai` 走 OpenAI 兼容接口（DeepSeek、Kimi、智谱、豆包、OpenAI 等）。每个用途配成"提供方:型号"，例如 `LIFE_MODEL_SKILL=deepseek:deepseek-chat`，不写前缀用默认提供方（百炼）。换模型只改 `.env`，再跑一遍评测集。客户端在第一次用到时才创建，没用到的提供方不填 Key 也能启动。

默认用千问：Spring AI Alibaba 支持最完整，国内访问稳定，以后做产品没有合规问题。各家型号更新很快，下表是档位，具体型号按当时在售的选。

| 用途 | 档位 | 说明 |
|---|---|---|
| 顶层路由、意图识别、定时巡检 | Turbo / Flash 档 | 调用量最大，要便宜、要快 |
| 子任务、工具调用、对话摘要 | Plus 档 | 平衡效果和成本 |
| 行程规划、训练计划生成、周复盘 | Max 档 | 需要较强的推理和长上下文 |
| 截图识别（小票、器械屏幕、小红书截图） | VL 档 | 多模态 |
| 向量化（攻略、动作库、记忆检索） | text-embedding 系列 | 维度和 pgvector 表结构一致，换模型要重建向量 |

| 组件 | 选型 |
|---|---|
| 会话记忆 | Spring AI `ChatMemory`，自己实现 PostgreSQL 版 Repository；自用阶段直接读库，不加缓存 |
| 向量检索 | Spring AI `PgVectorStore` |
| Graph 断点 | 框架自带的 `PostgresSaver`（已确认 1.1.2.x 提供） |
| 结构化输出 | `.entity(Xxx.class)` 映射到 Java record（行程、训练计划等） |
| MCP | Spring AI MCP Client，接高德官方 MCP；以后接自建的 MCP 服务 |

### 6.4 数据与存储

| 类别 | 选型 | 说明 |
|---|---|---|
| 关系数据库 | PostgreSQL（使用 `pgvector/pgvector` 镜像） | 业务数据、`jsonb`、向量都在一个库里 |
| 向量 | pgvector | 数据量大时再拆出独立向量库 |
| 缓存 | Redis（Lettuce 客户端） | Sa-Token 登录态、外部接口缓存（天气 1 小时、POI 1 天、路线 6 小时）、限流计数 |
| 文件 | `StorageService` 接口，先存本地磁盘 | GPX、截图、小票图片；以后换 OSS 或 MinIO |
| 备份 | `pg_dump` 每天定时备份，保留 7 天，备份文件加密；每季度做一次恢复演练 | 自用阶段也要做，记忆和训练记录丢了无法恢复 |

### 6.5 前端与交互

| 类别 | 选型 | 理由 |
|---|---|---|
| 入口 | **Web 页面**（已确认） | 手机和电脑浏览器都能用；手机上可以添加到桌面，像 App 一样打开 |
| 框架 | **uni-app（Vue 3 + TypeScript + Vite）** | 现在编译成 H5 网页；S3 同一套代码编译成微信小程序 |

## 8. 身份与安全

- **Sa-Token + Redis。** 用不透明 Token，支持多端登录、踢下线、封禁；管理后台用单独的账号体系。
- **登录方式。** S0 用账号密码，管理员账号由初始化脚本创建；S2 内测用邀请码注册；S3 再加手机号验证码和微信登录。
- **个人访问令牌。** 给 iOS 快捷指令、ICS 日历订阅这类没法走登录的场景用。每个令牌只授予一种用途，可以随时吊销，数据库里只存哈希。
- **AI 链路里不调用 `StpUtil`。** 流式输出和 Graph 并行节点跑在其他线程，拿不到登录态。在 Controller 入口取一次身份，写入 Graph 状态（随断点一起持久化），工具通过 `ToolContext` 获取。
- **断点续跑时重新校验**当前登录用户就是这个会话的所有者，不能只看 threadId。
- **功能权限和数据权限分开。** 能不能用某个功能交给 Sa-Token；能不能看某个行程或账单，在业务层根据空间成员关系判断。
- **敏感数据。** 手机号加密存储；不收集身份证等用不到的信息；健康、财务记忆默认不进 Prompt；日志脱敏；支持导出和删除个人数据。
- **外部内容防注入。** 小红书、点评、网页、截图里的文字都是外部内容，只交给总结节点处理，这个节点不挂任何写操作工具。外部内容里出现的"指令"一律当作普通文本。
- **设备安全。** App 白名单，不含微信、银行、支付类 App；遇到支付页强制停下；每次任务留截图。

### 技能为什么单独成模块

这里有两个决定：按技能拆（技能 + 路由），以及每个技能单独一个 Maven 模块。前一个决定解决的是模型能力问题，要保留；后一个只是工程组织方式，可以调整。

**按技能拆，不用一个 Agent 挂全部工具：**

1. **工具少，选得准。** 出游一个技能就有十几个工具，加上高德 MCP 又是十几个；健身、记账加进来后会有五六十个。工具越多，模型选错工具、填错参数的概率越高。拆开后，每轮只给模型当前场景需要的十来个。
2. **省 Token，首字更快。** 工具说明每轮都要发给模型。路由用便宜的 qwen-turbo，后面的大模型就只需要看相关的工具和 Prompt。
3. **规则和模型各管各的。** 爬山的安全规则只放在出游场景，记账的规则（金额由代码计算）只放在记账场景，不会互相干扰。不同技能也可以配不同的模型。
4. **能单独评测。** 改了出游的 Prompt，只跑出游的用例。

跨场景的需求，比如"周六去爬山，前一天晚上提醒我"：日程、天气、记忆这些通用能力放在 `life-core`，哪个技能需要就挂上。出游技能自带日程工具，所以这句话在出游技能里就能做完，不用在技能之间切换。

**每个技能单独一个 Maven 模块：**

1. **由编译器管住依赖方向。** 技能模块只能依赖 `life-core`，技能之间互相看不见。要共用的东西只能放进 core。只靠包名约定，时间长了会被打破。
2. **加技能不改核心代码。** 新建模块，在 `life-api` 里加一行依赖，`SkillRegistry` 会自动发现它，路由器也就知道了。以后做产品，按用户或套餐开关技能也有现成的边界。
3. **数据跟着模块走。** 每个模块带自己的迁移脚本和版本号区间（出游 `V2_x`、健身 `V4_x`……），删一个技能时表也一起去掉。

**代价：**

- 自用、只有两个技能的阶段，多模块是为以后准备的。实际已经碰到过一次问题：单独构建 `life-api` 时用了旧的 core 包，只能从根目录完整构建。
- `life-skill-schedule` 几乎是空的。日程的工具和提醒在 core 里（出游、健身都要用），这个模块只有一个 `ScheduleSkill` 类。
- 每轮对话多一次模型调用（路由），首字大约慢几百毫秒。上一轮用的技能会传给路由器，追问时一般不会跳错。

**可选方案：**

- **A. 保持现状（当前做法）。** 健身、记账加进来后，多模块的好处才会明显。
- **B. 合并成一个 `life-skills` 模块。** 每个技能一个包，加一个 ArchUnit 测试保证技能之间不互相引用。模块少，构建简单，以后需要时再拆出去。

两种方案下，`LifeSkill` 接口这条边界都不变。

### 平台对外的主要接口

```java
// 技能：新增一个领域只需实现它
public interface LifeSkill {
    String id();
    String description();                    // 给路由 Agent 看
    List<String> routingExamples();
    CompiledGraph graph();
    List<ToolCallback> tools();

public interface ActionExecutor {
    String id();                             // "meituan-paotui-skill"
    ExecTier tier();                         // OFFICIAL / SEMI_AUTO / GUI_AGENT

    ActionPreview preview(ActionIntent intent, UserCtx ctx);     // 给用户确认

// 身份：业务代码只认 UserCtx，不管它来自 Sa-Token 还是以后的 OAuth2

// 其他可替换的实现位
```

## 10. 自用部署

前期没有 GUI Agent，不需要连手机。开发在自己电脑上；日常使用要放在一台**一直开着**的机器上，因为训练提醒、天气巡检这些定时任务要求服务一直在线，笔记本合盖就会漏掉。可以用一台云服务器，也可以用家里常开的小主机。

## 11. 路线图

每个阶段都有进入下一阶段的条件，没达到就先不扩展。

### S0 自用 MVP（业余时间约 6～8 周）

- 平台核心：账号密码登录、会话持久化、统一记忆、Graph 断点续跑、日程提醒、Bark 推送
- 出游技能：高德 MCP、天气、行程规划与版本化、爬山时间和风险规则（不做知识库检索）
- Web 页面：登录、对话（含行程卡片和地图）、行程详情、我的（记忆、偏好、推送设置）
- 评测集第一版、docker compose 部署、每日备份
- 管理接口：运行评测、重试失败任务，先通过 SpringDoc 页面调用

**进入 S1 的条件：** 自己连续两周每天都在用

### S1 自用增强（约 6～8 周，按顺序一项一项做）

1. 健身计划：生成计划、对话记录训练、训练提醒、周复盘、自动调整；爬山计入训练量
2. 内容总结 + 知识库：小红书、点评的分享链接或截图，总结成攻略要点存入知识库，出游规划时检索
3. 记账：旅行账单与 AA、日常消费记录、小票拍照识别
4. 管理后台第一版：Prompt 版本与评测、调用日志与成本、动作库、知识库

每做完一项，自己先用一两周，再开始下一项。

**进入 S2 的条件：** 健身计划连续执行 4 周；评测集全部通过

### S2 亲友内测（5～20 人，视反馈而定）

- 启用多用户（邀请码注册）和共享空间（家庭、旅行团）、配额限流
- 隐私说明、数据导出和删除、监控告警
- 管理后台：用户管理、封禁、配额、用户反馈；模型配置从配置文件挪进后台；外部服务调用量和额度；定时任务页面

**进入 S3 的条件：** 有人主动推荐给别人，每天的模型成本可控

### S3 产品化（按商务和合规进度推进）

- 微信小程序：承载已有技能（出游、健身、记账等）
- 合规：ICP；生成式 AI 服务需要备案还是登记，上线前向网信部门确认
- 计费；评估接入微信 AI 生态
- 登录：手机号验证码、微信登录
- 开放 API 和对外 MCP，引入认证中心
- 管理后台：计费与订单、数据导出和删除工单、多管理员角色权限
- 启用平台开放后的预留能力：酒店平台接口与多平台比价

### 延后：外卖与设备执行（暂不排期）

依赖外部平台或额外设备，等前面的技能稳定后再启动。接口和配置位已在第 4、5 节预留，启动时不用改上层代码。

- 美团跑腿 Skill：官方可用，启动时第一个做
- 外卖推荐与跳转（半自动）：按记忆推荐吃什么，生成美团 App 跳转链接
- GUI Agent：只支持美团 App，搜店、加购，停在付款页推送确认；需要闲置安卓手机，服务迁到家里小主机
- 外卖、跑腿订单自动记账
- 小程序跳转美团外卖并带联盟分佣（依赖 S3 的小程序）
- 美团外卖官方下单能力（等平台开放）
- 端侧 GUI（安卓 App 无障碍服务，产品阶段评估）

**启动条件：** S1 完成并且想做这块时；或者美团开放外卖相关能力时。GUI Agent 的验收标准：任务成功率稳定在 80% 以上。

## 12. 风险与边界

| 风险 | 应对 |
|---|---|
| 范围失控 | 一个技能没做到自己天天在用之前，不开下一个 |
| 外部数据拿不到 | 先做半自动和文件导入；能力不可用时只预留接口，不写爬虫，不逆向接口签名 |
| GUI Agent 不稳定 | 每步校验，失败降级到半自动；关键流程写成固定脚本，AI 只处理异常情况 |
| 平台风控封号 | 只用自己的设备和账号，低频操作；永远不操作微信 |
| 模型编造价格或营业时间 | 这类数据只能来自工具返回；校验节点核对工具结果 |
| 户外安全 | 雷暴、大风、天黑前下不了山等情况由代码规则判断，不交给模型；输出附免责说明 |
| 训练受伤、过度节食 | 训练量增幅、热量下限、伤病禁忌动作都由代码规则把关；提到胸痛、头晕等情况时提示就医；说明不替代医生或专业教练 |
| 隐私合规 | 敏感数据加密、单独授权、可导出可删除；分享出去的内容只用于个人决策，不二次分发 |
| 成本 | 路由和巡检用小模型或规则；天气、POI 结果走缓存；`t_llm_usage` 每天汇总，超过月度预算就推送提醒 |
| 提示注入 | 外部内容（小红书、网页、截图里的文字）只进总结节点，这个节点没有写操作工具；敏感动作一律要求确认 |
| 数据丢失 | 每日加密备份，保留 7 天；每季度做一次恢复演练 |
| 服务离线漏提醒 | 日常使用部署在常开的机器上；服务重启后补发错过的提醒 |
| 框架版本变化 | 开工时锁定 Spring AI Alibaba 和 Sa-Token 版本，对照官方示例确认 API 写法 |

## 13. 健身技能设计

### 13.1 功能

| 功能 | 说明 |
|---|---|
| 生成训练计划 | 按目标（增肌、减脂、力量、为爬山备战）、每周能练几天、器械条件（健身房、家用哑铃、徒手）、伤病史和训练经验生成周期计划 |
| 对话记录训练 | "卧推 60 公斤 5 组 5 个，最后一组很吃力"自动解析成每组数据；也可以拍器械屏幕或手表截图，由 qwen-vl 识别 |
| 自动调整 | 根据完成率和吃力程度（RPE）调整下周的重量和训练量；连续几周没进步就安排减量周 |
| 训练提醒 | 训练日写进日程；错过了自动顺延，不让计划整体错乱 |
| 周复盘 | 每周日推送：完成率、训练量趋势、体重趋势、下周调整建议，确认后生成新版本计划 |
| 身体数据 | 体重、体脂、围度的记录和趋势 |

### 13.2 和其他技能的联动

| 联动 | 例子 |
|---|---|
| 出游 | 出差或旅行期间，自动换成酒店健身房或徒手训练；"下个月去爬泰山"→ 提前 4 周加入腿部和心肺训练 |
| 爬山、跑步 | 计入训练量（下肢、有氧），第二天自动安排恢复或减量 |
| 外卖（启动后） | 减脂期推荐外卖时按热量和蛋白质筛选；"在减脂"这条记忆带过期时间 |
| 日程 | 训练和行程、会议冲突时自动调整到别的日子 |
| 天气 | 户外跑步先看天气和空气质量，不适合就换成室内训练 |

### 13.3 计划生成流程：计算交给代码，编排交给模型

```
收集信息：目标、每周天数、器械、伤病、训练经验 ── 缺信息 → 中断追问
   ▼
代码计算：基础代谢（Mifflin-St Jeor 公式）和每日消耗、蛋白质目标、
         估算 1RM（Epley：重量 × (1 + 次数/30)）、每个肌群的周训练量范围
   ▼
模型生成：在上面的约束内选动作、排周期，只能从动作库里选动作
   ▼
规则校验：伤病禁忌动作、周训练量增幅、休息日、同一肌群间隔
   ▼ 不通过 → 重新生成（最多 2 次）
用户确认 → 写入计划新版本 → 生成日程事件
```

记录训练和周复盘也是同一个子图里的分支：

- **记录训练**：解析 → 入库 → 更新进度；明显偏离计划时提示是否调整。
- **周复盘**：定时触发 → 分析 → 给出调整建议 → 中断等确认 → 生成新版本。

### 13.4 安全规则（由代码判断，不交给模型）

- 周训练量增幅不超过约 10%。
- 给饮食建议时，建议的每日摄入不低于基础代谢（S1 不做饮食记录，见 13.5）。
- 伤病记录对应的禁忌动作直接排除，比如膝盖有伤就排除跳跃类动作。
- 用户提到胸痛、头晕、关节剧痛时，停止给训练建议，提示就医。
- 输出附说明：不替代医生或专业教练。
- 伤病、病史这类文字记录加密存储，默认不进 Prompt，用到时按需注入。体重、体脂这类数值要做趋势统计，不做字段加密，靠访问控制和备份加密保护。

### 13.5 数据来源

| 来源 | 状态 | 说明 |
|---|---|---|
| 对话记录、截图识别 | ✅ S1 | 最主要的入口 |
| iOS 快捷指令同步 Apple 健康 | ✅ S1 | 设一个每天自动运行的快捷指令，把体重、步数、训练记录推到你的服务，用个人访问令牌鉴权。只适合自用 |
| 安卓 Health Connect | 🔲 | 需要自己开发安卓 App，产品阶段再做 |
| 华为、小米、Keep 等平台 | 🔲 | 没有面向个人开发者的开放接口，先用导出文件或截图 |
| 动作库 | ✅ S1 | 开源动作库（如 free-exercise-db，使用前确认许可证）翻译成中文，再按需补充 |
| 饮食记录 | 🔲 | 拍照估算热量误差大，S1 先不做；减脂需求强烈时再评估 |

## 14. 管理后台

要做，但分阶段做。自用阶段你既是用户又是管理员，S0 不单独做后台页面。

### 14.1 先分清两类功能

| 类型 | 放在哪 | 例子 |
|---|---|---|
| 用户自己的设置 | Web 页面的"我的" | 查看、修改、删除记忆；偏好和体能信息；推送设置；导出和删除自己的数据；行程和训练计划的历史版本 |
| 运营和维护 | 管理后台 | 知识库、动作库、Prompt、模型配置、评测、日志、成本、用户管理 |

记忆管理一定放在用户端。这是用户自己的数据，做成产品后也是合规要求；管理员默认看不到。

### 14.2 功能和阶段

| 模块 | 功能 | 阶段 |
|---|---|---|
| 评测 | 运行评测集，查看每条用例的结果，和上一次对比 | S0 接口，S1 页面 |
| 定时任务 | 主动巡检、周复盘等任务的运行记录，失败重试 | S0 接口，S2 页面 |
| 知识库 | 上传攻略和户外安全资料，查看切片，重建向量索引 | S1 |
| 动作库 | 动作的中文名、目标肌群、器械、禁忌，增删改 | S1 |
| Prompt 管理 | 各技能 Prompt 的版本、对比、回滚；发布前先跑评测集 | S1 |
| 调用日志与成本 | 工具调用记录、失败原因、每天的 Token 用量和费用 | S1 |
| 模型配置 | 各用途使用的模型型号和参数，修改后即时生效。在这之前写在配置文件里 | S2 |
| 外部服务 | 高德、天气、DashScope 的调用量、额度和错误率 | S2 |
| 用户管理 | 账号、封禁、配额、在线设备、踢下线 | S2 |
| 用户反馈 | 用户点踩的回答和反馈内容，可以一键加入评测集 | S2 |
| 计费与订单 | 套餐、订单、退款 | S3 |
| 合规工单 | 数据导出和删除请求的处理记录 | S3 |
| 管理员权限 | 多个管理员、角色和权限 | S3 |

### 14.3 技术方案

- **后端**：和主应用同一个服务部署，接口前缀 `/admin/api/v1`。用 Sa-Token 的独立账号体系（`StpLogic("admin")`），和用户登录互不影响。
- **敏感操作**：发布 Prompt、删除知识库、封禁用户这类操作要求二级认证，并写入 `t_admin_op_log`。
- **隐私**：管理员默认看不到用户的记忆、健康和财务数据；日志里的用户内容脱敏显示。确实需要查看时，要填写原因并留下记录。
- **前端**：单独的 `life-admin-web`，Vue 3 + TypeScript + Element Plus，基于开源后台模板（如 vue-pure-admin 或 Vben Admin，使用前确认许可证）。后台只在电脑上用，所以不用 uni-app。
- **Prompt 存数据库并带版本**：修改后先跑评测集，通过了再发布；线上按版本号加载，可以一键回滚。
- **S0 的过渡做法**：先把管理接口写好，用 SpringDoc 自带的接口调试页面调用，只对管理员开放；查数据直接用数据库客户端（如 DBeaver）。
- **省事的图表方案**：成本、调用量这类统计图，可以先用 Grafana 直接读 PostgreSQL，不用自己写图表页面。
