## 2. 原则

- **一套代码**：继续用 life-web（uni-app），手机优先；屏幕变宽时变成左导航 + 中间对话 + 右侧卡片/地图。以后编译成微信小程序。
- **工具结果直接变卡片**：工具查到的餐厅、航班、酒店、行程，后端直接推 `card` 事件给前端渲染；模型只写一两句点评。链接和价格不经模型转写，就不会写错，输出 Token 也少。
- **信任**：每个价格标"平台 · 查询时间"，注明以平台为准；比价按价格排，"推荐排序"只用评分和距离；推广链接标"含推广链接"。
- **不编数据**：没有评价条数就只显示评分；没有图片显示占位图标；没有门票数据就不显示门票标签。

## 3. 关键设计

### 3.1 卡片事件

`ChatEvent` 增加 `type=card`，带 `card: {kind, data}`：

| kind | 谁发 | 前端展示 |
|---|---|---|
| `requirement` | 出游技能信息不全时调 `askTripRequirements` | 需求卡（原型②），已知的预先填好 |
| `restaurants` | `findRestaurants` | 美食列表（原型⑦），带"加入行程" |
| `flights` | `compareFlights` | 机票比价（原型⑧） |
| `hotels` | `findAndCompareHotels` / `compareHotelPrices` | 酒店比价（原型⑨） |
| `trip` | `saveTrip` | 行程摘要卡，点开进详情（原型④） |
| `plan_options` | 阶段二 | 三套方案（原型③） |
| `trip_diff` | 阶段二 | 调整前后对比（原型⑪） |

实现方式：仿照 `CallRecorder` 的 scope，加一个 `CardSink`，工具里 `cards.emit(kind, data)`；编排器把它合进 SSE 流。卡片同时存进 `t_chat_message.metadata.cards`，刷新页面或翻历史时能还原。

### 3.2 结构化行程

用 `t_trip_version.itinerary`（早就预留了，一直没用）：

```json
{
  "days": [{
    "date": "2026-03-10",
    "items": [{
      "id": "d1-1", "type": "SPOT",          // SPOT / FOOD / HOTEL / TRANSPORT / FREE
      "name": "成都大熊猫繁育研究基地", "start": "09:00", "end": "12:00",
      "poiId": "B001...", "lng": 104.14, "lat": 30.73, "address": "...",
      "note": "近距离看熊猫，适合亲子", "cost": 55, "locked": false,
      "url": null                             // 美食带点评链接，酒店带预订链接
    }],
    "legs": [{"from": "d1-1", "to": "d1-2", "mode": "TAXI", "minutes": 25, "km": 12}]
  }],
  "budget": {"perPerson": 4800}
}
```

- `saveTrip` 的参数从 Markdown 改成上面这个结构（用 Java record 定义，Spring AI 自动生成 JSON Schema，比让模型手写 JSON 字符串稳）。
- 后端校验：日期在行程范围内、时间不重叠、地点用高德 POI 补坐标；校验不过把错误返回给模型改。
- `content`（Markdown）由后端从 JSON 生成，老页面和日程联动照旧能用。

## 4. 分阶段

### 阶段一：卡片和结构化行程（约 5 天）

> 2026-10-30 第一版完成：卡片事件、美食/机票/酒店/行程/需求卡、结构化行程和详情页、首页、蓝色配色。
> 还没做：行程地点补坐标（挪到阶段二和地图一起做）。实测一次完整规划约 100 秒、费用上限约 0.37 元（14 万输入 Token）。

| # | 后端 | 前端 |
|---|---|---|
| 1.1 | `card` 事件、`CardSink`、卡片存进消息 metadata | 对话页按 kind 渲染卡片；历史消息还原卡片 |
| 1.2 | 美食、机票、酒店工具发卡片，带平台和查询时间 | 美食卡、机票卡、酒店卡（原型⑦⑧⑨） |
| 1.3 | `askTripRequirements` 工具；提交后同行人、去过的地方写进记忆 | 需求卡（原型②），可跳过 |
| 1.4 | 行程改结构化 JSON，校验，补坐标，生成 Markdown | 行程详情：按天标签 + 时间线（原型④，先不带按钮） |
| 1.5 | — | 首页（原型①，示例问题写死）；底部导航"首页、行程、日程、我的"；宽屏布局 |

验收：说"帮我规划成都4天3晚，2大1小，预算5000"，先出需求卡，提交后出行程卡，点进去按天看，问"附近吃什么"出美食卡，问机票出比价卡。

### 阶段二：可调整（约 5 天）

| # | 内容 |
|---|---|
| 2.1 | 行程单项操作接口：保留（锁定）、删除、不感兴趣（写记忆）、换一个。每次操作生成新版本，可回退 |
| 2.2 | 换一个：高德周边搜同类地点，排除去过和不感兴趣的（原型⑤） |
| 2.3 | 自动重算：改动后用高德路径规划重算当天交通和时间，生成前后对比（原型⑪）。**问卷里遇到最多的问题，优先做** |
| 2.4 | 美食卡"加入行程"，插到当天最合适的时间段 |
| 2.5 | 三套方案：一次调用生成三套概要（亮点、人均），选定后再展开成完整行程，控制费用 |
| 2.6 | 地图页（原型⑥）：uni-app `<map>`，网页上配高德 |

### 阶段三：按需

- 粘贴小红书攻略转行程（文字先做；截图需要视觉模型）
- 拖拽排序（原型⑩）、收藏、我的行程分"进行中 / 收藏 / 历史"（原型⑫）
- 景点和餐厅图片（先试高德 POI 图片质量）
- 地点营业状态核对
- "我的"里的偏好和记忆查看、删除
- 门票（找到数据源再做）

### 部署（约 0.5–1 天，可穿插）

- Nginx 容器：托管网页静态文件，`/api` 转发后端，**SSE 关闭缓冲**
- Dockerfile 加 Node 构建阶段打包网页；后端镜像加 Node（飞猪 CLI 用）
- HTTPS 证书自动续期、每天 pg_dump 备份、生产环境强密码
- 建议阶段一完成后上线，在自己手机上真实使用

## 6. 风险

- **模型填结构化行程不稳**：deepseek-flash 可能漏字段或时间冲突。用校验 + 把错误返回让模型改，最多重试一次；还不行就保存并标"待调整"。
- **费用**：行程 JSON 比 Markdown 长。字段保持精简，坐标等由后端补，不让模型输出。
- **原型和数据对不上的地方**：评价条数、景点图片、门票价格暂时没有数据，页面按"没有就不显示"处理。
